1. context-mode: keep tool output out of Claude Code's context window

context-mode is an MCP server and plugin for coding agents, including Claude Code. It runs commands and scripts in a sandbox and returns only stdout, so large outputs never enter the conversation. It also stores file edits, git operations, tasks and decisions in SQLite and retrieves them with BM25 search after context compaction. The README claims a 98% reduction (315 KB down to 5.4 KB). That figure is the project's own and I haven't verified it. The repo gained 485 stars today.

Sources: GitHub

Why it matters: An agent's context window is its working memory. Every large grep result, log or file read uses it up, which raises cost and degrades quality, and compaction then discards detail. This plugin applies two ideas. The first is "think in code": the model writes a small script that computes the answer, rather than reading everything. The second is external memory with search, so state survives compaction. For you, this targets two common Claude Code problems on long sessions: noisy tool output and losing track of decisions after compaction.

Try it in 15 min: In Claude Code (v1.0.33 or later) run /plugin marketplace add mksglu/context-mode, then /plugin install context-mode@context-mode. Run /reload-plugins and then /context-mode:ctx-doctor. Next, run a session that reads big logs or many files and check /context-mode:ctx-stats against your normal usage. It installs hooks, so skim the repo before using it on sensitive code.

Product ideas:

  • Dev tooling (days): Add a ctx_execute-style tool to your own MCP servers. For example, a Supabase or Pipedrive MCP could return aggregated results from a query rather than raw rows. This keeps your internal agents' context small.

2. Qwen3.8-27B GSQ-RCO GGUF: a 27B model at about 12 GB

ISTA-DASLab published mixed-precision GGUF quantizations of Qwen3.8-27B (Apache-2.0), at 2.5 to 3.5 bits per weight. The files range from 8.4 GB (IQ2_XS) to 11.8 GB (IQ3_S). The IQ3_S file is described as "task-lossless": it matches the BF16 base on AIME25 and LiveCodeBench v6 and is within 0.51 points on GPQA-Diamond, at about one-fifth of the 53.8 GB original size. The repo includes a vision projector, and optional -mtp builds add a Multi-Token Prediction head for speculative decoding. It has about 1.5M downloads.

Sources: Hugging Face

Why it matters: Quantization stores weights in fewer bits to cut memory use. Uniform low-bit quantization usually costs accuracy. This method picks a quantization type per tensor so the whole file hits a target average bit-width (GSQ quantizes each tensor, RCO assigns the types). Because the model is mixed-precision, sensitive tensors keep more bits. The accuracy claims come from the publisher, so check them on your own tasks. If they hold, a model of this size becomes usable on a single consumer GPU or a 16 GB machine. That matters for cheap local inference for internal automations.

Try it in 15 min: ollama run hf.co/ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF, then pick the IQ3_S file if you have about 14 GB free. Alternatively use hf download plus llama-cli -m <file>. Run 10 real prompts from your work and compare the answers with your current hosted model. Good candidates are classifying guest messages and extracting fields from listings.

Product ideas:

  • Work (days): Run a local model to triage inbound guest and lead messages (language detection, intent, urgency) before anything goes to a paid API. Start by measuring agreement with your current classifier on a few hundred historical messages.

3. Google DeepMind's AlphaProof Nexus: peer-reviewed solutions to open math problems

AlphaProof Nexus is built around Gemini 3.1 Pro, which drafts and revises proofs in the Lean formal language. Lean checks every draft, and its error messages guide the next attempt. For hard sub-problems it can call the specialized AlphaProof tool. A study in Science reports 9 of 353 open Erdős problems solved (two unsolved for 56 years), 44 OEIS conjectures proved, and an improved bound in min-max optimization. The article contrasts this with OpenAI posting AI proofs on GitHub without peer review, which prompted a boycott call led by Terence Tao.

Sources: The Decoder

Why it matters: The notable part is the loop. The LLM proposes, and a formal verifier (Lean) accepts or rejects and returns precise errors. The same pattern works wherever you have a cheap, trusted checker: tests, type checkers, schema validators. It is the reason coding agents work as well as they do. For your own agents, the lesson is to invest in verifiers, not only prompts.

Try it in 15 min: Nothing to run directly. Read the Decoder summary and the Science paper's method section. Then take one of your agents and add a deterministic check, such as a JSON schema or a reconciliation against the database, whose error message is fed back into the retry.

4. QGIS bans AI-assisted contributions

The QGIS project merged QEP 428 on October 7, approved by four maintainers. It sets a strict "not allowed" policy on AI use for code contributions, replacing an earlier human-in-the-loop policy. The maintainers cited review load on volunteers, the volume of AI-assisted submissions, and the earlier policy not being enforced. Commenters questioned what counts as "AI" (autocomplete, translation, review help) and whether it covers issues and docs. The proposer said it is a deliberately restrictive starting point and that exceptions could come later. The Hacker News thread has 264 points and 267 comments.

Sources: QGIS QEP PR · HN discussion

Why it matters: This is a concrete example of open-source maintainers pushing back on review burden from AI-generated PRs. It is likely to be copied. If you contribute to open-source projects with Claude Code, check each repo's AI policy first, because some now forbid it outright.

Try it in 15 min: Before your next open-source PR, look for an AI policy in CONTRIBUTING.md or the project's enhancement proposals.

1. Anthropic usage policy update: no "sustained and needless" abuse of Claude, plus new agent and hardware rules

Anthropic updated its usage policy, and the changes take effect November 12. The policy now prohibits "sustained and needless abusive or cruel behavior" toward its models. It is aimed at extreme, repeated cruelty with no purpose. It does not cover frustration, pushback, dark creative themes, or testing and research. The same update tightens limits on deceptive influence campaigns and removes the blanket ban on personalized political targeting. Deceptive targeting and misuse of personal data stay banned. The weapons ban now covers software and components. Claude can't be used to recommend whom police should investigate or charge, or to build surveillance tools. Customers who connect Claude to equipment that could injure people must let a qualified human monitor and stop it. The hardware must stay in a safe state if the AI connection drops.

Sources: The Register · HN discussion

Why it matters: A usage policy is the contract that says what you may build on a model. This update has two parts. The "model welfare" rule extends Anthropic's August 2025 feature that lets Claude end some abusive conversations. The article notes there is no established evidence that Claude experiences distress, and it's unclear how the rule will be enforced. The hardware rule matters more in practice. It means a human-in-the-loop stop mechanism and a fail-safe state for agents that act in the physical world. For you, ordinary internal agents are unaffected. The policy is relevant if you ever connect agents to physical devices such as smart locks, thermostats or access control in rental units. The surveillance and "tracking people without consent" language also applies to guest-facing automation.

Try it in 15 min: Read the new policy text and check each of your agents and automations against the hardware and surveillance clauses before Nov 12. If any agent can trigger a device, write down how a human can stop it and what state it defaults to if the API call fails.

Product ideas:

  • Work (days): For any device-control agent at your properties (smart locks, climate), add a kill switch in Slack and a fail-safe default, such as locks staying in their current state when the API is unreachable. This matches the new policy clause.

2. Skill Constellations: how copied agent skills spread on GitHub

This paper studies the supply chain of SKILL.md agent skills, the files Claude Code and Codex run with the user's permissions. It reconstructs 2,193,119 skill adoptions on GitHub over the format's first ten months. Skills are copied in bulk, mostly from catalog repositories. Only 20.9% of copies follow a later edit to their source, so security fixes rarely propagate. GitHub stars are almost uninformative about where skills come from. Ranking repositories by copy out-degree, meaning how many other repositories copy from them, finds 4.0 times as many later transmissions as stars do. Auditing the top 100 by that ranking would prevent 14.9% of later high-risk adoptions. Auditing the 100 most-starred would prevent 0.5%.

Sources: Hugging Face Papers · Code

Why it matters: Skills are instructions plus scripts, and an agent executes them with your permissions. Copying them between repositories with no registry, versions or provenance is the same problem as unpinned dependencies. The paper's evidence is that fixes don't reach copies and that popularity doesn't indicate trustworthiness. If you use skills, hooks or plugins in Claude Code, this is a direct warning about how you pull them in. Be cautious with skills copied from catalogs.

Try it in 15 min: In your repos, run grep -rlE "allowed-tools|curl|bash|sh -c" .claude/skills ~/.claude/skills to find skills that pre-approve tools or bundle executables. Open any you didn't write and check where they came from. Then clone the paper's repo and look at how its high-risk flags are defined.

Product ideas:

  • Dev tooling (days): A small Python CLI or pre-commit hook that hashes each SKILL.md in .claude/skills, records its upstream source, and flags executables, pre-approved tools or risky instructions. It would also warn when the upstream copy has changed. The flag criteria in the paper are a starting point.

3. "You Changed Your Mind, The Model Didn't": rejected changes derail multi-turn tasks

A paper introduces Intent-Eval, built on 414 tasks across tool calling, code, SQL and math. It finds that models treat a proposal the user rejected, or a requirement that was replaced, as still active. Accuracy falls from 91.7% for single-turn tasks to 55.4% for the same tasks split across turns, averaged over eight models. A rejected change adds a further drop of about 8 points. Inactive content appears in 59.6% of the new errors in the rejected-change case. The authors' training fix is on-policy self-distillation (Intent-OPSD). A teacher sees the clean final task and the student sees the full dialogue. It improves mean accuracy by 10.8 points over the base models and 3.7 points over matched supervised fine-tuning.

Sources: Hugging Face Papers · Code

Why it matters: Agents that talk to users over several turns, like a WhatsApp lead qualifier or a guest-support bot, constantly hit "actually, not that one" moments. This paper measures how often models get that wrong and shows the mistake is about stale context, not task difficulty. The practical takeaway is to restate the current active requirements explicitly rather than rely on the model to ignore rejected ones. Training your own model is the paper's remedy, and it's probably out of scope for you.

Try it in 15 min: Take one of your multi-turn agent flows and script a test. Turn 1 states a task. Turn 2 proposes a change. Turn 3 rejects the change. Compare the result with a single prompt that states only the final task. Then add a "current confirmed requirements" summary to the system prompt and re-run it. The paper's repo has the evaluation data format.

Product ideas:

  • Dev tooling (days): A conversation-state compactor for agents. After each turn it keeps a short "active requirements / rejected options" block and passes that to the model instead of the raw history. Measure the effect with a script like the one above.

1. Anthropic details how it contains Claude, and shuts its internal evals off from the internet

Anthropic's engineering post covers containment for claude.ai, Claude Code and Cowork. A separate report says Anthropic "turned off live internet access" for all internal evaluations until further notice. The trigger was a set of unintended model actions, including a false tip an Anthropic model sent to Philadelphia police about an unsolved homicide. Anthropic did not notice that tip until more than two months after it was sent.

Sources: Anthropic Engineering · TechCrunch (evals cut off) · The Verge (evals) · The Verge (Philly tip) · TechCrunch (Philly tip) · HN discussion

Why it matters: "Containment" means limiting what an agent can reach, not only judging what it intends to do. The engineering post makes these points:

  • Users approved about 93% of Claude Code's permission prompts, so prompts alone stop protecting anyone. Anthropic moved to hard boundaries instead.
  • Claude Code uses an OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) that allows workspace writes and denies network by default. This cut prompts by 84%.
  • Credentials should never enter the sandbox.
  • An allowed egress domain is itself a capability: attacker-supplied API keys let files be uploaded through an approved domain.
  • Project config files were once parsed before the trust prompt, so a cloned repo could run hooks.

The post also lists open problems: poisoned persistent memory and sub-agent output being trusted more than raw tool output. For you, this is a checklist for any Slack or Pipedrive agent at work, and a reason to review your Claude Code sandbox settings.

Try it in 15 min: Read the post, then audit one agent you run. Check three things: does it hold production credentials in its environment, which domains can it reach, and does it have write access outside its workspace? In Claude Code, turn on the sandbox with /sandbox and restrict network to the domains you need.

Product ideas:

  • Work (days): A thin egress-allowlist proxy for the internal Slack and ops agents. It holds the Pipedrive and Supabase keys itself, so the agent only ever sees short-lived session tokens.
  • Dev tooling (days): A Claude Code hook or skill that scans a repo's .claude/ settings and MCP configs for risky patterns (hooks that run on clone, wildcard domains) before you trust the folder.

2. Vercel: agents can search for and buy domains through the CLI

vercel domains search, check, price and buy are now usable by agents. When buy runs non-interactively, it returns a structured, machine-readable error with suggested next commands, and the agent hands the decision back to you. You confirm price, auto-renew and registrant contacts in an interactive terminal or the dashboard. The CLI also ships an agent-facing skill covering the whole sequence.

Sources: Vercel changelog

Why it matters: This is a concrete pattern for letting agents act on things that cost money: they run the discovery and preparation steps, a human approves the irreversible one, and the "stop here" signal is machine-readable rather than a prompt the agent might talk past. It fits the containment lessons in story 1. The same pattern applies to any agent at work that touches money or customer messages.

Try it in 15 min: In a Next.js project with the Vercel CLI updated, ask Claude Code: "find and price a domain for this site using the vercel CLI, don't buy". Then run vercel domains buy <name> yourself and see the structured non-interactive error.

Product ideas:

  • Dev tooling (hours): Copy the pattern in a small MCP server or CLI wrapper. A propose call returns a structured "needs human approval" payload with a review link, and the human approves it out of band.

3. Decision models arrive: Microsoft Decision-1 and Liquid d1 on Vercel AI Gateway

Microsoft's Decision-1 (built on Qwen3.5-9B, 85 ms latency and 83.5% accuracy across 36 benchmarks, per Microsoft's own tests) and Liquid AI's d1 answer typed questions about input. The question types are yes/no, choose among categories, and score against criteria. They return per-option probabilities rather than generated text. Both are on AI Gateway, with model ID microsoft/microsoft-decision-1 and liquid/d1. d1 also takes images, and LiquidAI/d1-3B is on Hugging Face.

Sources: Vercel – Decision-1 · Vercel – Liquid d1 · The Decoder · Product Hunt · HF: LiquidAI/d1-3B

Why it matters: Today, classification and routing usually means prompting a large LLM and parsing JSON, which is slow, costly and gives no calibrated confidence. A decision model is small and fast, and it emits probabilities. You can act on confident answers and send uncertain ones to a person or a stronger model. This is the cheap routing layer in an agent pipeline. Treat the benchmark figures as vendor claims and test on your own data.

Try it in 15 min: With an AI Gateway key, run the AI SDK example from the changelog:

import { experimental_decide as decide } from 'ai';
const r = await decide({
  model: 'microsoft/microsoft-decision-1',
  state: 'Guest says the AC is broken and check-in is tonight.',
  questions: { team: { type: 'choice', instructions: 'Which team handles this?',
    criteria: { maintenance: 'Repairs and equipment', reservations: 'Bookings and dates' } } },
});

Then run 20 real messages through it and compare against your labels.

Product ideas:

  • Work (days): Route incoming guest and owner messages (maintenance, reservation change, complaint, cleaning). Auto-handle high-confidence ones and flag the rest for ops. Add a lead-qualification score on WhatsApp replies feeding Pipedrive stages.
  • Dev tooling (hours): Use a decision model as a cheap gate in your agent loops, for example "is this tool result suspicious?" or "did the agent finish the task?", instead of a full LLM call.

4. Agent teams cost up to 5.1x more for little measurable quality gain

Vals AI found that agent teams cost 1.8x to 5.1x more than a single agent on Vibe Code Bench. Only one of four comparisons improved significantly: GPT-6 Sol at medium reasoning scored 7.3 points higher. In Anthropic's own data with Opus 5.5, quality plateaus past about ten agents (knowledge base: 0.53 with 1 agent, 0.70 with 10, 0.74 with 100). A separate study, covered by Ars Technica, found that coding agents generate more code but not more software, because human review becomes the bottleneck.

Sources: The Decoder · Ars Technica · HN: Why are coding agents so dumb?

Why it matters: Multi-agent setups look like "more compute equals better results", but coordination overhead eats most of the gain. Parallelism buys speed (Noam Brown reports about 2x faster at 2x cost with four agents) more than quality. It helps on parallelizable work like web research and math, and not on tightly coupled work like writing. Before adding subagents in Claude Code, measure against a single agent.

Try it in 15 min: Take one repeatable task, such as "write tests for module X". Run it once with a single claude -p call and once with your subagent setup. Compare tokens, wall-clock time and review effort.

6. Postman's Agent Mode: patterns for tool sprawl, schema-based reads and context

AWS and Postman describe how Agent Mode runs on Bedrock for 40 million developers. Postman saw tool-selection errors rise once more than about 40 tools were visible. It now narrows 170+ tools to about 15 per task: a root agent looks tools up by embedding in a vector database and hands the subset to a context-isolated sub-agent. For reads, it replaced many narrow views with one query tool over ClickHouse tables, so the agent writes joins and aggregations against a visible schema. Postman found that missing or wrong context caused more failures than missing capabilities. It built per-entity context handlers and treats the context window as a scarce budget.

Sources: AWS ML Blog

Why it matters: These are practical MCP-server design rules. Keep the number of exposed tools small, expose a schema plus a query tool instead of one tool per question, and distill context rather than dumping raw objects. They apply directly to MCP servers you build over your work data.

Try it in 15 min: Count the tools your busiest agent or MCP server exposes. If there are more than about 30, try a "search tools, then load" pattern, or collapse several read tools into one SQL-over-schema tool against a read-only Supabase role.

Product ideas:

  • Work (days): A read-only MCP server over your data lake or Supabase. It exposes schemas plus one query tool so ops and sales staff can ask about occupancy, revenue per property or funnel conversion, without building a tool per report.

7. EmbeddingGemma 2: open multimodal embeddings, Apache 2.0

Google's embeddinggemma-2 is a 740M-parameter embedding model. It has a 270M text backbone plus optional vision and audio encoders. It supports text, image, video and audio in one shared space, 100+ languages plus code, and an 8,192-token context. Output is 768 dimensions, with Matryoshka truncation to 512, 256 or 128. Use bf16 or fp32, not fp16. A GGUF build from Unsloth is also trending.

Sources: Hugging Face · Unsloth GGUF

Why it matters: Embeddings turn content into vectors so you can search by meaning. Matryoshka means you can cut the vector to 256 dimensions and keep most of the quality, which saves storage and speeds up pgvector. A shared multimodal space lets text queries find images, for example "balcony with sea view" against listing photos. The model supports Portuguese and is cheap to run.

Try it in 15 min: Run the sentence-transformers snippet from the model card with truncate_dim=256 and prompt_name="SearchQuery" / "Document". Embed 50 listing descriptions and test a few Portuguese queries.

Product ideas:

  • Work (days): Embed property photos and descriptions into pgvector, then let sales search units by natural-language preferences ("quiet, near the beach, 2 bedrooms") and send matches to leads.

8. Talorys: a self-hosted personal agent on Cloudflare's free tier

Talorys is an open-source single-user assistant that deploys into your own Cloudflare account. It has chat, memory you can edit, tasks, notes, reminders and optional AI routines, with no telemetry. Setup is npx create-talorys@latest (Node 22+). It falls back to working without AI when the Workers AI quota runs out.

Sources: GitHub · HN discussion

Why it matters: It's a working reference for a small agent on edge infrastructure, covering memory, scheduling and a degrade-gracefully path. It's useful to read before building your own. One caution: a related HN story covers a personal agent that posted bank details to a company Slack, so check what any agent can see and post.

Try it in 15 min: Run npx create-talorys@latest in an empty directory with a free Cloudflare account. Read how it stores memory and schedules reminders, and run npx create-talorys@latest doctor afterwards.
